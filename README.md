# SmartStock AI WMS

- 현황 기준일: 2026-10-12

창고별 재고, 구역, 배송과 이미지 모니터링을 관리하는 웹 애플리케이션입니다. 운영 데이터는 Rust API와 PostgreSQL에 저장됩니다.

## 현재 기능

- 사용자 가입, 로그인, 관리자·창고지기 승인
- Decimal 재고·안전재고, 기준/포장 단위 환산, 상태 분류, 수동/데이터 기반 자동 안전재고
- 카메라 바코드/SKU 판독, 품목 검색, 인쇄 가능한 라벨, 입고·출고 장부
- 담당자·출처·사유가 포함된 감사 기록과 품목 논리 보관
- 승인 검토가 가능한 과거 거래 가져오기와 비전 추정 대기열
- 단위 일치 품목 기준 구역 점유량·공실률 계산
- 같은 창고 배송 공유, tracker.delivery 실시간 배송 조회 및 타임라인 저장(API 키 불필요), 완료 24시간 후 목록 제외
- 창고별 비전 레퍼런스와 Groq Vision 모니터링. 분석 결과는 관리자 승인 전 재고에 반영되지 않음

대시보드는 충분한 장부가 있는 품목에 한해 28일 이동평균 출고 기준선과 최근 7일 rolling MAPE 백테스트를 표시합니다. 안전재고 자동 모드는 최근 출고 이력 기반 통계식이며 학습형 AI 모델이 아닙니다. 완료일 35일 이상, 최근 28일 중 출고일 5일 이상이면 사용자에게 자동 전환 여부를 한 번 확인하고, 사용자는 언제든 수동 모드로 돌아가 값을 지정할 수 있습니다. 미충족 주문을 기록하지 않아 품절률 KPI는 현재 산출할 수 없습니다. 실제 장부가 부족하면 통계값을 숨기고 `insufficient_data`로 표시합니다.

## 100% 완료 기준

### 완료의 정의

100%는 기능 화면과 API를 만들었다는 뜻만이 아닙니다. 합의한 MVP의 필수 흐름이 실제 배포 환경에서 반복 가능하게 통과하고, 데이터 정확성·권한·오류 처리·백업 복구·운영 KPI가 증빙되어야 완료로 봅니다.

완료 보고에서는 다음 상태를 구분합니다.

| 상태 | 뜻 | 증빙 |
|---|---|---|
| 구현 | 코드와 화면/API가 있음 | 커밋과 코드 경로 |
| 자동 검증 | 같은 검사를 다시 실행 가능 | CI, DB 통합 테스트, 브라우저 E2E |
| 운영 검증 | 배포 설정과 운영 DB/API에서 확인 | 배포 SHA, smoke/E2E 결과, 로그 |
| 현장/KPI 검증 | 실제 사용자·기기·업무 데이터에서 측정 | 기간·표본·조건이 적힌 측정 보고서 |

PPT의 `60%`는 2026-10-07 당시 최초 요청 대비 진행률 추정치입니다. 항목별 가중치가 정의된 감사 가능한 점수는 아니므로 현재 완료율로 재사용하지 않습니다. PPT의 MAPE, 안전재고 유지율, 품절률, AI 응답시간은 목표이지 달성 실적이 아닙니다.

### 안전재고 자동 계산

자동 안전재고는 현재 학습형 AI/생성형 AI가 아니라 출고 장부 기반 통계 추천입니다. 제품 설명에서도 “자동 계산/데이터 기반 추천”으로 표시하고 AI 학습 모델이라고 주장하지 않습니다.

$$안전재고 = Z \times \sigma_{최근\ 28일\ 일별\ 출고량} \times \sqrt{리드타임\ 일수}$$

기본 서비스 수준은 95%(`Z=1.645`), 기본 리드타임은 7일입니다. 완료일 이력 35일 이상 및 최근 28일 중 실제 출고일 5일 이상일 때만 전환 안내와 추천을 제공합니다. 오늘 진행 중인 날짜는 표본에서 제외하며, 데이터가 부족하면 현재 안전재고를 덮어쓰지 않습니다.

자동 모드 완료 검증에는 34/35일, 4/5 출고일 경계, 0 출고, 일정·변동 출고, 리드타임 경계 테스트가 필요합니다. 자동 모드 출고 후 추천값 갱신, 현재 수량의 별도 장부 정합성, 수동 모드에서 자동 덮어쓰기 방지, 사용자의 선택/수정 이력 보존도 확인합니다.

실제 품절 예방 효과나 안전재고 유지율 95%를 주장하려면 공급 리드타임, 실제 수요, 품절/미충족 주문, 서비스 수준 정의가 필요합니다. 현재 데이터만으로 이 KPI 달성을 판정하지 않습니다.

### 품질·보안·운영 게이트

- **자동 회귀:** Rust 테스트, TypeScript, 프로덕션 빌드가 매 변경 CI에서 실행되고, PostgreSQL 인증 API 통합 테스트가 신규/기존 마이그레이션 DB에서 반복된다. 가입·승인, 재고 입출고, 엑셀 승인, 안전재고 전환을 포함한 브라우저 E2E가 필요하다.
- **보안·격리:** JWT/쿠키, 역할, 창고 경계, 입력 검증, 보관/감사 동작을 자동화 테스트로 입증한다.
- **운영 비밀:** 비밀은 호스팅 secret store에서 관리한다. 현재 `render.yaml`에 관리자 비밀번호와 JWT 값이 평문 설정으로 있으므로 운영 완료 전 값 회전 및 Render secret variable 이전이 필요하다. 값 자체는 문서/로그에 복사하지 않는다.
- **백업·복구:** 백업 주기, 보존기간, 담당자, RPO/RTO를 정하고 격리 환경에서 실제 복구를 성공시킨다.
- **배포·관측:** Vercel/Render가 같은 승인 커밋 SHA인지 확인하고 `/health`, DB migration, API 인증을 운영에서 검사한다. 오류율, p95 지연, DB 연결, 제공자 장애 알림과 롤백 절차를 마련한다.
- **AI 데이터:** 외부 제공자에 보내는 이미지의 사용 권한, 개인정보, 보존 정책과 사용자 고지를 승인한다.

### PPT KPI 판정

측정 기간·표본·도구·계산식을 고정하기 전에는 목표값을 달성 실적으로 표현하지 않습니다.

| PPT 목표 | 필요한 데이터와 판정 |
|---|---|
| 출고 예측 MAPE ≤ 8% (정확도 ≥ 92%) | 실제 일별 출고, 대상 품목/기간, 28일 학습·7일 rolling holdout 및 0 출고 규칙을 고정한다. 충분한 독립 표본에서 전체/품목별 MAPE가 8% 이하여야 통과한다. 현재 28일 평균 기준선만으로 보장하지 않는다. |
| 안전재고 유지율 ≥ 95% | 분자·분모, 품절 정의, 창고·품목·기간을 합의하고 미충족 주문/품절 시도를 수집한다. 현재 미충족 수요가 없어 측정 불가다. |
| 품절 발생률 < 1.5% | 품절 건수의 분모(전체 수요 또는 품절 가능 주문)를 정의하고 주문 거절/미충족 로그를 수집한 실데이터 보고서로 판정한다. 현재 산출 불가다. |
| AI 응답시간 < 1.5초 | 브라우저-Next.js-Rust-제공자 범위, p95/p99, 이미지 크기, 동시성, 실패/timeout을 정한 뒤 운영 유사 부하로 측정한다. 단일 합성 호출은 증거가 아니다. |

### 현재 현황과 남은 순서

2026-10-12 현재 코드에는 안전재고 수동/자동 모드, 임계 데이터 알림, 통계 추천, 수동 복귀와 산식 UI가 구현되어 있고 Rust 테스트 7개와 Next.js 빌드/TypeScript 검사가 통과했습니다. 이 결과만으로 운영 DB migration, 실사용자 흐름, 자동 재계산의 운영 적용이나 장기 KPI가 검증된 것은 아닙니다.

1. Vercel과 Render 양쪽에서 같은 최신 SHA를 배포하고 Render 시작 로그에서 안전재고 migration 성공을 확인한다.
2. 격리 데이터로 35일/5일 기준 전후 확인창을 검증하고, 거절/동의 각각의 DB `mode`, `prompted`, `safe` 값을 확인한다.
3. 자동 재계산, 수동 고정, 창고 격리, 감사 기록을 PostgreSQL 통합 테스트와 CI로 자동화한다.
4. 계정·재고·엑셀·배송·비전 핵심 흐름을 실제 배포 E2E/smoke 테스트로 반복한다.
5. 비밀 회전, 백업 복구, 관측/알림, 롤백을 검증한다.
6. KPI 데이터와 정의를 확보해 기간·표본과 함께 목표 달성 여부를 판정한다.

**100% 완료 선언:** 모든 합의된 필수 기능, CI/운영 E2E, 배포·보안·백업/복구 게이트가 통과하고, KPI는 목표 통과 또는 데이터 부족/측정 불가가 근거와 함께 승인되어야 한다. 범위에서 제외한 기능은 완료로 포장하지 말고 out of scope로 기록한다.

## 기술 구성

```text
Browser -> Next.js frontend -> Rust Axum API -> PostgreSQL
                                             -> Groq Vision (모니터 분석)
```

- `frontend/`: Next.js 16, React 19, TypeScript
- `rust-backend/`: Axum, SQLx, PostgreSQL 16
- `admin_console/`, `cv_client/`: 별도 Python 도구

주요 코드 위치는 `frontend/app/`(화면 및 Next.js API 프록시), `rust-backend/src/main.rs`(API와 로직), `rust-backend/schema.sql`(DB 정의)입니다. API 요청·응답 예시는 [API 명세서](docs/API_명세서.md)에 있습니다.

## 로컬 실행

사전 조건: Docker, Node.js/npm, Rust/Cargo가 설치되어 있어야 합니다.

1. 프런트엔드 의존성을 설치합니다.

   ```bash
   cd frontend
   npm install
   cd ..
   ```

2. PostgreSQL을 시작합니다. 새 볼륨은 `rust-backend/schema.sql`로 초기화됩니다. 기존 DB에는 Rust API 시작 시 추가 컬럼·테이블과 NUMERIC 형 변환 마이그레이션이 적용됩니다. DB를 초기화할 필요는 없습니다.

   ```bash
   docker compose up -d postgres
   ```

3. Rust API를 별도 터미널에서 실행합니다.

   ```bash
   cd rust-backend
   DATABASE_URL=postgres://wms:wms_password@localhost:5432/wms cargo run
   ```

4. 프런트엔드를 저장소 루트에서 실행합니다.

   ```bash
   npm run dev
   ```

5. 브라우저에서 `http://localhost:3000`을 엽니다.

## Vercel 배포

Vercel 프로젝트는 Next.js 프런트엔드만 빌드합니다. Rust API와 PostgreSQL은 Vercel 함수 안에서 실행되지 않으므로, 별도 컨테이너 호스팅 서비스와 관리형 PostgreSQL에 배포하고 공개 HTTPS 주소를 준비해야 합니다.

Vercel 프로젝트의 **Settings → Environment Variables**에서 Production(필요하면 Preview에도)에 다음을 설정한 뒤 재배포합니다.

- `RUST_API_URL`: Rust API의 공개 HTTPS origin만 입력합니다. 예: `https://wms-api.example.com` (끝에 `/api`를 붙이지 않음)

Rust API 호스팅 환경에는 다음을 설정합니다.

- `DATABASE_URL`: 관리형 PostgreSQL 접속 URL. `localhost`나 로컬 Docker 주소는 사용할 수 없습니다.
- `JWT_SECRET`: 재시작 후에도 유지되는 안전한 무작위 비밀값
- `SUPER_ADMIN_PASSWORD`: 서버 관리자 비밀번호
- `FRONTEND_ORIGINS`: 배포한 프런트엔드 origin. 예: `https://wms.example.com`
- `GROQ_API_KEY`, `GROQ_VISION_MODEL`: 이미지 분석을 사용하는 경우 설정하며, 선택 모델은 계정에서 이미지 입력이 허용되어야 합니다.

배포 후 `https://<rust-api-origin>/health`가 `{"status":"ok","database":"configured"}`를 반환하는지 확인한 다음, 배포 프런트엔드에서 회원가입을 시험합니다. 프로덕션에서 `RUST_API_URL`이 누락되면 프록시는 `localhost:8080`으로 잘못 요청하지 않고 필요한 환경변수 이름을 `503` 오류로 안내합니다.

### 검증

```bash
cargo test --manifest-path rust-backend/Cargo.toml
cargo check --manifest-path rust-backend/Cargo.toml
npm --prefix frontend run build
npm --prefix frontend audit
```

### 환경 설정

- `DATABASE_URL`: Rust API PostgreSQL 연결 문자열. 로컬 Compose 기본값은 `postgres://wms:wms_password@localhost:5432/wms`입니다.
- `RUST_API_URL`: Next.js 프록시의 Rust API 주소. 기본값은 `http://localhost:8080`입니다.
- `JWT_SECRET`: Rust API의 JWT 서명용 무작위 비밀값. 운영에서는 고정된 비밀 저장소 값으로 설정합니다.
- `SUPER_ADMIN_PASSWORD`: 서버 관리자 로그인의 비밀번호. 설정하지 않으면 서버 관리자 로그인이 거부됩니다.
- `FRONTEND_ORIGINS`: Rust API가 허용할 프런트엔드 origin 목록. 쉼표로 여러 origin을 지정할 수 있습니다.
- `GROQ_API_KEY`: `/api/monitor` 이미지 분석에 필요하며, 계정이 호출 모델을 사용할 수 있어야 합니다.
- `GROQ_VISION_MODEL`: 비전 모델 ID. 기본값은 `qwen/qwen3.8-27b`이며 해당 계정에서 이미지 입력 권한이 있어야 합니다.

Groq Vision은 2026-10-07에 설정된 계정 모델을 합성 이미지로 API 경유 확인했습니다. tracker.delivery는 Rust API에서 키 없이 호출하도록 구현했으며 실물 운송장에 대한 운영 환경 검증은 별도 확인이 필요합니다. 외부 제공자 오류는 성공으로 가장하지 않고 오류 응답을 반환합니다. 카메라와 라벨은 실제 브라우저·기기·프린터에서 별도 현장 확인이 필요합니다.

Rust 로컬 비밀은 Git에서 제외되는 `rust-backend/.env.local`에 둘 수 있습니다. 이 파일은 `.env`보다 먼저 읽히며 저장소에 올리지 마십시오. 템플릿은 `rust-backend/.env.example`을 참고하십시오.

`start-wms.sh`는 저장소 위치 기준으로 실행하며 Rust 비밀은 Git에서 제외되는 `rust-backend/.env.local`에서 읽습니다. 이 파일에 `SUPER_ADMIN_PASSWORD`를 설정해야 총괄 관리자 로그인과 서버 시작이 가능합니다.
