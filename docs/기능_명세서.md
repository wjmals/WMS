# WMS 기능 명세서


현재 저장소 구현 기준의 기능, 주요 흐름과 제한사항이다. API 요청·응답은 [API 명세서](API_명세서.md), 컬럼 및 제약조건은 [schema.sql](../rust-backend/schema.sql)을 기준으로 한다. 구현된 API가 모두 실제 배포 환경에서 검증된 것은 아니다.

## 사용자와 접근

| 역할 | 흐름 |
|---|---|
| 서버 관리자 | 관리자 가입 요청을 검토·승인하고 계정을 관리한다. 현재 내장 계정은 코드에 정의되어 DB 사용자 행으로 저장되지 않는다. |
| 관리자 | 가입 후 `PENDING_ADMIN` 상태가 된다. 서버 관리자 승인 시 전용 창고가 생성되며, 창고지기 가입 요청을 승인한다. |
| 창고지기 | 가입할 때 담당 관리자 이메일이 필요하다. `PENDING_WAREHOUSE`로 시작하며 승인 시 관리자의 창고에 배정된다. |

승인 상태는 `PENDING_ADMIN`, `PENDING_WAREHOUSE`, `APPROVED`를 사용한다. 로그인 요청은 `POST /api/users`의 `action=login`이며 Rust API가 12시간 만료 JWT를 발급한다. Next.js는 토큰을 `HttpOnly`, `SameSite=Lax` 쿠키에 저장하고 API 프록시 요청에 Bearer 토큰으로 전달한다. Rust API는 토큰을 검증하고 일반 계정의 현재 역할·승인 상태·창고 배정을 DB에서 다시 확인한다. 브라우저의 `wms_auth_user` 값은 화면 표시용이며 권한 근거가 아니다.

### 주요 승인 흐름

```text
관리자 가입 -> PENDING_ADMIN -> 서버 관리자 승인 -> 창고 생성 및 배정
창고지기 가입(adminEmail 필요) -> PENDING_WAREHOUSE -> 관리자 승인 -> 창고 배정
```

비밀번호는 일반 가입 시 Argon2 해시로 DB에 저장된다. 서버 관리자 로그인에는 `SUPER_ADMIN_PASSWORD` 환경변수가 필요하다. 사용자 초대 흐름의 기본 비밀번호 정책은 운영 환경에서 별도 개선·검증이 필요하다.

## 화면 경로

| 경로 | 역할 | 동작 |
|---|---|---|
| `/` | 로그인 사용자 | 재고 요약과 창고 현황 대시보드 |
| `/login`, `/signup` | 공개 | 로그인 및 역할별 가입 |
| `/barcode` | 로그인 사용자 | 바코드/SKU 판독, 소수·포장 단위 입출고, 품목 라벨 인쇄 |
| `/delivery` | 로그인 사용자 | 배송 등록, 상태 전이 및 삭제 |
| `/monitor` | 로그인 사용자 | 카메라/이미지 분석, 레퍼런스 및 이력 관리 |
| `/report` | 로그인 사용자 | 저장된 재고를 바탕으로 위험 정보 표시 |

화면의 로그인 가드는 사용자 경험을 위한 처리이며 보안 경계는 Rust API의 JWT·역할·창고 인가다. 재고·구역·레퍼런스·모니터 요청에서 일반 계정은 DB에 배정된 창고만 접근할 수 있다. 배송도 창고 ID로 분리한다. 서버 관리자만 전역 사용자 목록·관리자 승인 등 명시된 전역 작업을 수행한다.

## 기능

| 영역 | 구현 동작 |
|---|---|
| 대시보드·재고 | 창고별 품목을 조회한다. 소수 수량과 기준/포장 단위 환산을 지원한다. 수정 시 Decimal 안전재고 기준으로 상태와 차이를 계산한다. 삭제는 장부를 보존하는 논리 보관이다. |
| 바코드 업무 | ZXing으로 카메라 프레임의 바코드/QR을 판독하고 창고 내 코드, 품목 ID 또는 이름으로 재고를 찾는다. 소수 및 포장 단위 입출고는 사유·담당자와 장부에 저장하고 품목 라벨을 인쇄한다. |
| 과거 거래·감사 | 엑셀 거래를 검증 후 승인 대기로 등록한다. 관리자가 시간순 잔량과 기초 잔액을 승인해야 공식 장부에 들어가며 현재 잔량은 바꾸지 않는다. 장부에는 출처, 작업자, 사유를 남긴다. |
| 구역 | 창고별 구역을 생성·조회·갱신·삭제한다. 구역 용량 단위와 같은 기준 단위를 가진 품목만 합산해 점유량, 공실률과 경고 상태를 계산한다. |
| 배송 | 택배사를 선택해 운송장 번호를 등록하고 SweetTracker API로 실제 배송 단계·위치·타임라인을 갱신한다. API 키가 없는 환경에서는 조회를 성공으로 표시하지 않는다. 완료 후 24시간이 지나면 조회 목록에서 제외된다. |
| 비전 레퍼런스 | 창고에 품목명·설명·이미지를 등록하고 조회·삭제한다. Excel `.xlsx`/`.xls`에서 최대 500행까지 일괄 가져오며 이미지 파일명 또는 내보낸 워크북의 포함 이미지 데이터를 사용한다. 전체 레퍼런스는 워크북으로 내보낸다. 이미지 data URL은 최대 50,000자다. |
| 모니터링 | 이미지와 창고 ID를 전달해 분석한다. 서버는 창고 레퍼런스를 최대 3개 사용하고 결과를 로그와 승인 대기 추정치로 저장한다. 관리자가 승인해야 재고가 갱신된다. |
| 출고 기준선·백테스트 | 최소 28일 학습 이력과 7일 검증 구간이 있을 때 28일 이동평균 출고 기준선 및 최근 7일 rolling MAPE를 표시한다. 데이터 부족·비영 출고 표본 부재 시 측정 불가로 반환한다. |
| 리포트 | 현재 저장된 재고를 중심으로 위험 정보를 표시한다. 장기간 시계열 예측이나 예측 정확도는 검증된 기능으로 보장하지 않는다. |

입출고 변동은 장부에 시점별로 기록되며 대시보드는 최근 30일의 실제 입고·출고/조정과 과거 구간 비교를 보여준다. 추가로 단순 28일 이동평균을 다음 7일 출고 기준선으로 계산하고 최근 7일을 rolling-origin 방식으로 백테스트한다. 학습형 AI 예측과 권장 발주량은 제공하지 않으며, 주문 미충족 이벤트를 저장하지 않아 품절률은 계산하지 않는다. 과거 거래 가져오기는 관리자 승인 후에만 장부에 들어가고 현재 잔량을 변경하지 않는다.

## 주요 규칙

- 재고 부족: `current < safe × 0.5`; 적정: `safe × 0.5 ≤ current ≤ safe × 2`; 과다: `current > safe × 2`.
- 재고, 구역, 레퍼런스, 모니터 로그, 배송은 창고별로 저장된다. 접근 요청은 관리자 이메일 기준으로 기록된다.
- AI 분석은 요청 시 창고 레퍼런스를 사용하는 추론이다. 모델 파인튜닝이나 정확도 보장을 뜻하지 않는다.
- 이미지 수량 추정은 승인 전에는 잔량을 변경하지 않는다. 승인/반려 행위에는 담당자와 사유를 기록한다.
- 품목 보관 처리는 물리 삭제가 아니다. 원시 장부는 FK 제한으로 보호되며 감사 로그와 함께 보존된다.
- `GROQ_API_KEY`가 없으면 분석을 수행할 수 없고, 외부 제공자 오류나 응답 파싱 실패는 오류로 처리한다.
- JWT 서명에는 고정된 비밀 `JWT_SECRET`, 서버 관리자 로그인에는 `SUPER_ADMIN_PASSWORD`가 필요하다. 미설정 시 서버 관리자 로그인은 거부되며 임시 JWT 키를 사용한 세션은 재시작 때 만료된다.
- 레퍼런스는 추론 참고 자료이며 모델 파인튜닝이 아니다. 수집 데이터의 출처·사용 권한·라벨 품질·보존 기간을 관리해야 한다.

## 검증 상태

2026-10-07 현재 Rust 단위 테스트 5개, Next.js 프로덕션 빌드/TypeScript 검사, npm 보안 감사(취약점 0건)를 통과했다. 별도 임시 PostgreSQL DB와 인증된 API로 Decimal 생성, 포장 단위 입출고, 과거 장부 승인, 비전 승인, 보관·감사 보존, 구역 단위 집계, 레퍼런스 CRUD, 배송 상태 전이, 음수 재고 거부를 검증했다. 35일 일정 출고 시계열의 예측 기준선·rolling MAPE, Groq Qwen Vision의 WMS API 경유 및 승인 흐름도 합성 데이터로 검증했다. 현재 운영 DB는 비어 있어 운영용 실측 KPI는 아직 표시되지 않는다. 임시 DB는 검증 후 제거했다.

Groq 계정에서 기존 Llama 비전 모델은 접근 불가였고, 계정이 제공하는 `qwen/qwen3.8-27b` 모델을 설정해 2026-10-07 합성 이미지 호출을 WMS API 경유로 성공시켰다. 이는 실제 비전 경로 작동 확인이지 이미지셋 기반 정확도 검증은 아니다. 운영 DB는 품목·장부가 0건이라 실측 MAPE와 품절률은 산출할 수 없다. `SWEET_TRACKER_API_KEY`는 미설정이며, 실물 카메라/프린터와 여러 사용자 계정의 가입·승인 전 과정은 별도 현장 검증이 필요하다. CI 자동화 통합 테스트 제품군은 현재 단위 테스트 및 일회성 격리 API 검증과 별개로 추가해야 한다.
