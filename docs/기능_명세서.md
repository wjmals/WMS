# WMS 기능 명세서

현재 저장소 구현 기준의 기능, 주요 흐름과 제한사항이다. API 요청·응답은 [API 명세서](API_명세서.md), 컬럼 및 제약조건은 [schema.sql](../rust-backend/schema.sql)을 기준으로 한다. 구현된 API가 모두 실제 배포 환경에서 검증된 것은 아니다.

## 사용자와 접근

| 역할 | 흐름 |
|---|---|
| 서버 관리자 | 관리자 가입 요청을 검토·승인하고 계정을 관리한다. 현재 내장 계정은 코드에 정의되어 DB 사용자 행으로 저장되지 않는다. |
| 관리자 | 가입 후 `PENDING_ADMIN` 상태가 된다. 서버 관리자 승인 시 전용 창고가 생성되며, 창고지기 가입 요청을 승인한다. |
| 창고지기 | 가입할 때 담당 관리자 이메일이 필요하다. `PENDING_WAREHOUSE`로 시작하며 승인 시 관리자의 창고에 배정된다. |

승인 상태는 `PENDING_ADMIN`, `PENDING_WAREHOUSE`, `APPROVED`를 사용한다. 현재 로그인 요청은 `POST /api/users`의 `action=login`이며 사용자 정보는 브라우저의 `wms_auth_user`에 저장된다. `AuthGuard`는 화면 접근을 제어하지만 Rust API에 서버 측 세션/JWT 권한 검사는 없다. 따라서 화면 보호를 서버 보안 경계로 간주하지 않으며, 운영 배포 전 API 인증·인가가 필요하다.

### 주요 승인 흐름

```text
관리자 가입 -> PENDING_ADMIN -> 서버 관리자 승인 -> 창고 생성 및 배정
창고지기 가입(adminEmail 필요) -> PENDING_WAREHOUSE -> 관리자 승인 -> 창고 배정
```

비밀번호는 일반 가입 시 Argon2 해시로 DB에 저장된다. 다만 내장 서버 관리자 자격증명은 코드에 있으며, 초대 흐름의 기본 비밀번호도 운영 전에 교체해야 한다.

## 화면 경로

| 경로 | 역할 | 동작 |
|---|---|---|
| `/` | 로그인 사용자 | 재고 요약과 창고 현황 대시보드 |
| `/login`, `/signup` | 공개 | 로그인 및 역할별 가입 |
| `/barcode` | 로그인 사용자 | 품목 ID/이름 검색, 재고 확인·수량 조정 |
| `/delivery` | 로그인 사용자 | 배송 등록, 상태 전이 및 삭제 |
| `/monitor` | 로그인 사용자 | 카메라/이미지 분석, 레퍼런스 및 이력 관리 |
| `/report` | 로그인 사용자 | 저장된 재고를 바탕으로 위험 정보 표시 |

화면의 로그인 가드는 현재 브라우저 상태 기반이다. 각 API 요청에 서버가 사용자의 역할을 강제하는 구조는 아직 구현되어 있지 않다.

## 기능

| 영역 | 구현 동작 |
|---|---|
| 대시보드·재고 | 창고별 품목을 조회한다. 생성·수정·삭제 API가 있으며 수정 시 현재/안전 재고 기준으로 상태, 차이 텍스트와 권고를 계산한다. 음수 재고 값은 허용되지 않는다. |
| 바코드 업무 | 입력한 품목 ID 또는 이름으로 재고를 찾고 입고·출고 수량을 반영한다. 재고 조회 기본 창고는 `wh_wjmals`이며 사용자의 창고 ID가 요청에 전달된다. |
| 구역 | 창고별 구역을 생성·조회·갱신·삭제한다. 식별자는 `(warehouseId, id)` 조합이며 온도, 상태, 용량, 품목 메타데이터를 저장한다. |
| 배송 | 운송장 번호에서 숫자 외 문자를 제거해 등록한다. 상태는 `AT_PICKUP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED`로 수동 전이한다. 완료 후 24시간이 지나면 조회 목록에서 제외된다. |
| 비전 레퍼런스 | 창고에 품목명·설명·이미지를 등록하고 조회·삭제한다. 이미지는 base64 텍스트로 저장하며 서버 저장 길이는 최대 50,000자다. |
| 모니터링 | 이미지와 창고 ID를 전달해 분석한다. 서버는 창고 레퍼런스를 최대 3개 사용하고 결과를 로그로 저장하며, 일치하는 품목이 있으면 재고를 갱신한다. |
| 리포트 | 현재 저장된 재고를 중심으로 위험 정보를 표시한다. 장기간 시계열 예측이나 예측 정확도는 검증된 기능으로 보장하지 않는다. |

바코드 화면에서 카메라 영상을 볼 수 있지만 카메라 프레임의 실제 바코드 판독은 구현되어 있지 않다. 택배사 실시간 추적, 재고량에 따른 공실률 자동 산출, 검증된 수요 예측은 제공한다고 간주하지 않는다.

## 주요 규칙

- 재고 부족: `current < safe × 0.5`; 적정: `safe × 0.5 ≤ current ≤ safe × 2`; 과다: `current > safe × 2`.
- 재고, 구역, 레퍼런스, 모니터 로그는 창고별로 저장된다. 배송과 접근 요청 테이블에는 창고 외래 키가 없다.
- AI 분석은 요청 시 창고 레퍼런스를 사용하는 추론이다. 모델 파인튜닝이나 정확도 보장을 뜻하지 않는다.
- `GROQ_API_KEY`가 없으면 분석을 수행할 수 없고, 외부 제공자 오류나 응답 파싱 실패는 오류로 처리한다.
- 운영 배포 전 서버 측 인증·인가, 내장 관리자 자격증명, 초대 기본 비밀번호, CORS 설정을 검토해야 한다.

## 인수 확인

- [ ] 가입·로그인·관리자 승인·창고지기 승인 흐름에서 상태와 창고 배정이 일치한다.
- [ ] 재고 CRUD, 경계값 상태 분류, 음수 거부와 DB 저장값을 확인한다.
- [ ] 구역은 창고별로 분리되며 같은 창고에서 중복 ID를 만들지 않는다.
- [ ] 배송 상태 전이와 완료 후 24시간 조회 제외를 확인한다.
- [ ] 레퍼런스는 창고별 분석에만 전달되고 AI 성공/실패 응답이 구분된다.
- [ ] 무로그인·다른 창고 요청이 서버 API에서 차단되는지 확인한다. 현재 서버 권한 검사가 없으므로 운영 전 완료해야 한다.
