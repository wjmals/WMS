## 1. 100%의 의미

100%는 화면과 API를 만들었다는 뜻만이 아니다. 합의된 MVP의 모든 필수 흐름이 실제 배포 환경에서 재현 가능하게 통과하고, 데이터 정확성·권한·실패 처리·복구·운영 KPI의 측정 결과가 증빙되어야 완료로 본다.

완료율을 보고할 때는 다음 네 상태를 구분한다.

| 상태 | 의미 | 완료 증빙 예시 |
|---|---|---|
| 구현 | 코드와 화면/API가 존재한다 | PR/커밋, 코드 경로 |
| 자동 검증 | 같은 조건으로 다시 실행할 테스트가 있다 | CI 테스트 결과, DB 통합 테스트 |
| 운영 검증 | 실제 배포 설정과 운영 DB/API에서 확인했다 | 배포 SHA, smoke/E2E 기록, 로그 |
| 현장/KPI 검증 | 실제 사용자·기기·업무 데이터에서 목표를 측정했다 | 데이터 기간·표본·측정 보고서 |

PPT의 2026-10-07 `60%`는 당시 최초 요청 대비 구현 진행률로 제시된 추정치다. 계산식과 항목별 가중치가 정의된 감사 가능한 점수는 아니므로 현재 완료율로 재사용하지 않는다. PPT의 예측 정확도, 안전재고 유지율, 품절률, 응답시간 수치는 목표값이며 달성 실적이 아니다.

## 3. 자동재고 계산 기준

현재 자동 안전재고는 학습형 AI나 생성형 AI가 아니라 출고 장부에서 계산하는 통계적 추천이다. 제품 설명과 UI는 이를 “자동 계산/데이터 기반 추천”으로 표시하고 AI 학습 모델이라고 주장하지 않는다.

$$안전재고 = Z \times \sigma_{최근\ 28일\ 일별\ 출고량} \times \sqrt{리드타임\ 일수}$$

기본 서비스 수준은 95%(`Z=1.645`), 기본 리드타임은 7일이다. 자동 계산 제안은 완료일 데이터 35일 이상 및 최근 28일 중 실제 출고가 있었던 날 5일 이상일 때만 가능하다. 오늘 진행 중인 날짜는 표본에서 제외한다. 데이터가 부족하거나 분산 계산이 불가능하면 기존 안전재고를 유지하고 자동 계산값을 적용하지 않는다.

이 계산을 100%로 판정하려면 다음 검증이 모두 통과해야 한다.

- 고정된 일별 출고 데이터에 대해 추천값이 독립 계산 결과와 허용 정밀도 내에서 일치한다.
- 완료일 34일/35일, 출고 발생 4일/5일 경계, 모두 0인 출고, 일정 출고, 변동 출고, 리드타임 범위를 자동 테스트한다.
- 자동 모드에서 출고 기록 후 추천값과 상태가 갱신되고, 현재 수량은 별도로 기록된 거래량만큼만 변한다.
- 수동 모드에서는 출고가 생겨도 사용자가 설정한 안전재고가 자동 덮어쓰기 되지 않는다.
- 안내 거절/동의 여부, 현재 모드, 추천값, 리드타임, 수동 수정 이력이 DB와 감사 기록으로 추적된다.

실제 품절 예방 효과 또는 안전재고 유지율 95%를 주장하려면 공급 리드타임, 실제 수요, 품절/미충족 주문과 서비스 수준의 정의가 필요하다. 현재 데이터만으로 그 KPI가 달성됐다고 판정하지 않는다.

## 4. 품질·보안·운영 게이트

### 자동 회귀

- Rust 단위 테스트, TypeScript 검사, Next.js 프로덕션 빌드가 매 변경에서 CI로 실행된다.
- PostgreSQL을 사용하는 인증 API 통합 테스트가 새 DB와 기존 스키마 마이그레이션 DB 양쪽에서 반복된다.
- 최소 한 개의 브라우저 E2E가 가입/승인, 재고 입출고, 엑셀 승인, 안전재고 모드 변경을 끝까지 확인한다.
- 실패 테스트는 응답 코드·오류 원문·로그 trace ID로 원인을 찾을 수 있다.

### 보안·데이터

- JWT/쿠키 보안, 역할별 권한, 창고 간 격리, 입력 검증, 삭제/보관 및 감사기록을 자동화 테스트로 입증한다.
- 운영 비밀은 저장소에 없고 호스팅 비밀 저장소에서 관리한다. 현재 `render.yaml`의 관리자 비밀번호/JWT 값은 공개 설정 파일에 평문으로 있으므로 운영 100% 완료 전 비밀 회전 및 Render Secret Environment Variable 이전이 필요하다.
- 백업 주기, 보존기간, 복구 담당자와 RPO/RTO를 정하고 격리 환경에서 실제 백업 복구를 성공시킨다.
- 외부 AI로 보내는 이미지의 권리·개인정보·보존 정책과 사용자 고지를 승인한다.

### 배포·관측

- Vercel과 Render가 같은 승인 커밋 SHA로 배포됐음을 확인한다. `/health`의 DB 연결, API 인증, DB migration을 실제 운영에서 확인한다.
- 오류율, p95 지연시간, DB 연결/풀 고갈, 외부 제공자 실패와 배포 실패를 볼 수 있는 로그/알림이 있다.
- 롤백 절차와 DB 스키마 호환 전략을 실제로 연습한다.
- 실제 운영 계정이 있는 상태에서 중요 시나리오를 smoke test하고 결과를 날짜·커밋·환경과 함께 기록한다.

## 5. KPI 100% 판정

KPI는 정의·표본·기간·측정 도구가 고정된 다음에만 판정한다. 목표값 통과 전까지는 “구현 완료”와 “KPI 달성”을 구분한다.

| PPT 목표 | 측정 정의 및 필요한 데이터 | 100% 판정 증빙 |
|---|---|---|
| 출고 예측 MAPE ≤ 8% (정확도 ≥ 92%) | 예측 대상 품목/기간, 일별 실제 출고, 28일 학습·7일 rolling holdout, 0 출고일 처리 규칙을 사전 고정한다. | 독립 검증 기간과 충분한 비영 출고 표본에서 전체 및 품목별 MAPE 보고서가 8% 이하. 현재 28일 평균 기준선 결과만으로 보장하지 않음. |
| 안전재고 유지율 ≥ 95% | 유지율의 분자/분모, 품절 정의, 측정 창고·품목·기간을 먼저 합의한다. 미충족 주문/품절 시도 데이터가 필수다. | 재고·미충족 수요가 연결된 실측 보고서에서 목표 통과. 현재 미충족 주문을 저장하지 않아 측정 불가. |
| 품절 발생률 < 1.5% | 품절 사건 수 ÷ 전체 수요 또는 품절 가능 주문 수 등 denominator 정의가 필요하다. | 주문/수요 거절 로그가 포함된 실데이터 기간에서 목표 통과. 현재 산출 불가. |
| AI 응답시간 < 1.5초 | 브라우저-Next.js-Rust-제공자 구간, p95/p99, 이미지 크기, 동시성, 실패/timeout 포함 여부를 합의한다. | 운영과 유사한 부하·네트워크에서 분포 보고서가 목표 통과. 현재 합성 단일 호출은 지연 KPI 증거가 아님. |

## 6. 현 상태와 다음 순서

최근 구현은 코드 수준에서 수동/자동 안전재고 선택, 임계 데이터 알림, 통계식 추천, 수동 복귀와 공식 확인창을 추가했다. Rust 테스트·프런트 빌드가 통과했다. 이것만으로 운영 배포, 기존 DB migration, 실제 알림·자동 재계산, 장기 KPI 달성이 증명되지는 않는다.

남은 100% 게이트의 권장 순서:

1. `eaa6353`을 Vercel과 Render 양쪽에 배포하고 Render 시작 로그에서 안전재고 migration 성공을 확인한다.
2. 수동 모드 품목에 합성 완료일/출고 데이터를 35일 이상 넣어 최근 출고일 5일 경계 전후의 확인창을 검증한다. 거절과 동의 각각에서 DB의 mode/prompted/safe 값을 확인한다.
3. 자동 모드에서 새 출고 후 safe 재계산, 수동 편집 후 manual 고정, 창고 간 격리와 감사 기록을 PostgreSQL 통합 테스트로 자동화한다.
4. 핵심 계정·재고·엑셀·배송·비전 흐름을 CI와 실제 배포 smoke test로 반복한다.
5. 백업 복구, 운영 비밀 회전, 관측/알림 및 롤백을 완료한다.
6. KPI 정의에 필요한 실데이터를 수집한 뒤 기간과 표본을 공개하고 목표 달성 여부를 판정한다.

**100% 완료 선언 조건:** 필수 기능 게이트가 전부 통과하고, CI 및 운영 E2E 증빙이 있으며, 배포·보안·백업/복구 게이트가 통과하고, KPI는 목표 통과 또는 “데이터 부족/측정 불가”가 투명하게 승인된 상태여야 한다. 범위에서 제외한 기능은 미완료로 숨기지 말고 명시적으로 out of scope로 남긴다.
