# SmartStock AI WMS 프로젝트 제안서

- 기준일: 2026년 10월 7일
- 목표 완료일: 미정. 구현과 검증 상태를 기준으로 범위를 갱신한다.

## 보도자료

### 재고와 배송 정보를 한 흐름으로 관리하는 SmartStock AI WMS

SmartStock AI WMS는 창고 운영자가 품목별 현재 재고와 안전재고, 보관 구역, 배송 상태를 한 웹 서비스에서 확인하도록 돕는 창고관리시스템이다. 사용자는 역할별 승인 절차를 거쳐 담당 창고에 접근하고, 재고 변경은 Rust API를 통해 PostgreSQL에 저장한다.

핵심 기능은 역할·창고별 승인, Decimal 재고와 포장 단위 환산, 입출고 장부·감사 기록, 관리자 승인 기반 과거 거래 및 비전 추정 반영, 구역·배송 관리다. Rust API는 JWT와 DB 사용자 재검증을 적용하며, 기존 PostgreSQL의 수량 컬럼은 시작 마이그레이션으로 `NUMERIC(20,6)`으로 전환한다. 비전 레퍼런스는 엑셀로 등록·내보낼 수 있지만 모델 파인튜닝이 아니라 요청 시 참고 이미지로 전달된다.

현재 저장소의 구현과 검증 가능한 범위를 기준으로 한 제안이다. 고객 인터뷰와 현장 데이터가 없어 시간·오류·비용 절감이나 AI 정확도를 성과로 주장하지 않는다. 코드 빌드 성공과 서비스 설정·현장 검증 완료를 구분하고, 재현 가능한 통합 테스트와 별도 현장 실증을 진행한다.

### 한눈에 보는 제안

- 고객: 재고와 출고 흐름을 관리하는 창고 관리자와 현장 창고지기
- 문제: 재고·구역·배송·승인 정보가 나뉘어 상태 확인과 조치 판단이 번거롭다.
- 제안: 창고 단위 데이터와 승인·재고 변경을 하나의 웹 업무 흐름으로 연결한다.
- 요청: 서버 측 권한 경계, 창고별 데이터 격리, 수량·단위 정합성, 승인·감사 흐름을 실제 API와 DB로 검증한다.

### 완성 시 사용자가 확인할 수 있는 것

관리자는 승인된 팀원과 창고 재고를 확인하고, 창고지기는 품목의 Decimal 현재량·안전량을 기준 단위 또는 포장 단위로 입출고 기록한다. 관리자는 과거 거래와 비전 추정치를 검토·승인하며 현재 잔량 변경의 담당자·출처·사유는 감사 장부에 남는다. 품목 보관은 논리 처리여서 기존 장부를 보존한다.

이는 제공할 업무 기능에 대한 약속이며 데이터 정확성, AI 신뢰성, 시간 단축을 보장하지 않는다. 재고와 배송의 자동 연동도 범위에 포함하지 않는다.

예를 들어 안전재고가 100이고 현재 수량이 40인 품목은 서버 규칙에 따라 부족으로 표시된다. 운영자는 품목을 찾아 입고량을 반영하고, 변경된 수량과 상태를 다시 확인한다. 이 시나리오는 업무 기능을 설명하는 예이며 실제 현장 데이터나 효과 측정 결과는 아니다.

범위는 재고 기록과 운영 판단을 지원하는 데 한정한다. ERP 발주, 공급사 주문, 백그라운드 주기 택배 추적은 자동화하지 않는다. 배송 상세는 작업자가 SweetTracker 조회를 요청할 때 갱신한다.


## 문제와 사용자

### 해결할 문제

재고, 보관 구역, 배송 정보가 서로 다른 자료에 있으면 운영자는 수량이 안전 기준에 미달했는지, 어떤 조치가 필요한지 함께 판단하기 어렵다. 관리자와 창고지기의 계정 승인 및 창고 배정이 운영 정보와 분리되면 잘못된 창고 데이터에 접근하거나 승인 상태를 따로 확인해야 한다.

문제의 빈도와 우선순위는 아직 조사되지 않았다. 현장 인터뷰와 테스트로 확인할 가설이다.

### 대상 사용자

- 창고 관리자: 창고 재고·구역·배송과 팀원 승인을 관리한다.
- 창고지기: 현장 품목을 조회하고 입출고 수량을 조정한다.
- 서버 관리자: 관리자 계정 승인과 사용자 관리를 담당한다.

### 제공 가치

창고별 재고·구역·모니터링을 한곳에서 조회하고, 재고 조정 시 서버가 안전재고 기준의 상태·차이·권고를 다시 계산한다. 승인된 창고지기는 배정된 창고에서 조회와 조정을 수행한다.

배송은 창고별로 분리 저장되지만 재고 품목과 직접 연결되지는 않는다. 작업자 요청형 SweetTracker 조회를 지원하지만 백그라운드 주기 추적은 제공하지 않는다. 업무 적합성과 도입 효과는 프로토타입 검토 및 현장 시나리오 테스트로 확인한다.

### 기존 업무와 제안 흐름

제안 흐름은 검증할 가설로, `가입·승인 → 창고 배정 → 재고 조회·조정 → 상태 확인 → 배송·모니터링 기록 확인` 순이다. 데모에서는 재고 변경 후 API 응답, DB 값, 화면 표시가 일치하는지 확인한다.

### 기존 방식과의 비교 가설

| 관점 | 분리된 수기·스프레드시트 방식에서 확인할 문제 | 제안 시스템이 제공하는 기준 |
|---|---|---|
| 재고 판정 | 기준량·계산 시점이 사용자마다 다를 수 있음 | 서버의 동일한 안전재고 판정 규칙 |
| 변경 추적 | 변경값과 화면 표시를 별도 확인해야 할 수 있음 | API 응답과 PostgreSQL 저장값을 대조 |
| 사용자 소속 | 계정 승인과 담당 창고 정보가 분리될 수 있음 | 승인 단계에서 warehouse ID 배정 |
| AI 결과 | 이미지 판단과 실제 재고가 따로 기록될 수 있음 | 요청 이미지 분석 결과와 모니터 로그 보관 |

표는 조사 결과가 아니라 비교 가설이다. 도입 전 같은 과업에서 누락·오입력·처리시간을 비교한다.


## 해결 방향과 목표

### 제품 원칙

- **사용자 업무 우선:** 로그인·승인, 재고 조회·조정 등 일상 업무의 완결성을 우선한다.
- **데이터로 검증:** 화면 표시뿐 아니라 API 응답과 PostgreSQL 저장 결과를 함께 확인한다.
- **실패를 숨기지 않음:** DB·네트워크·AI 오류를 구분하고 성공으로 오인시키지 않는다.
- **범위 유지:** 필수 업무 전 고급 예측·에이전트·다중 카메라를 추가하지 않는다.
- **효과를 과장하지 않음:** 측정하지 않은 정확도·절감 효과를 성과로 기재하지 않는다.

### 현재 완료·검증 기준

| 범위 | 완료 조건 | 확인 자료 |
|---|---|---|
| 계정·승인 | JWT 발급, 역할·창고별 권한 및 미인증 거부 구현 | 실사용자별 가입·승인 현장 검증 필요 |
| Decimal 재고 | 소수 수량, 기준/포장 단위 환산, 서버 상태 계산 구현 | 숫자 정밀도와 단위 정의는 업무 기준에 맞춰 검토 필요 |
| 장부·보관 | 담당자·출처·사유 기록, 논리 보관, 장부 물리 삭제 제한 구현 | 감사 로그 보존·백업 정책을 운영 환경에서 설정해야 함 |
| 과거 거래 | 엑셀 배치 임시 저장, 관리자 승인, 기초·중간 잔액 검증 구현 | 실제 고객 원본 파일 형식과 대용량 운영 검증 필요 |
| 구역·배송 | 단위 일치 구역 집계, 배송 CRUD 및 상태 전이 구현 | SweetTracker 성공 호출은 키·이용권이 있는 환경에서 확인 필요 |
| 비전 검토 | 분석 로그와 승인 대기 추정치 분리, 승인 후에만 재고 반영 | `GROQ_API_KEY`, 모델 권한 및 실제 현장 이미지 검증 필요 |

현재 규칙은 `current < safe × 0.5` 부족, `safe × 0.5 ≤ current ≤ safe × 2` 적정, 그 초과는 과다다. 경계값은 운영자 검토가 필요하며, 성능·AI 정확도 목표는 측정 기준이 정해진 뒤 설정한다.

### 성공 측정 방법

현장 데이터, 응답 시간 기준, 라벨이 있는 AI 이미지셋이 아직 없다. 다음 검증 단계에서 핵심 시나리오 통과 여부와 재고 판정 정합성을 기록하고, 데이터 확보 후 다음을 측정한다.

- 업무 성공률: 사전에 정한 가입·승인·재고·배송 테스트 사례 중 통과한 사례의 비율
- 데이터 정합성: 화면·API 응답·DB에 기록된 재고와 창고 ID가 일치하는지
- 처리 성능: 고정된 데이터와 환경에서 API 응답 시간 및 오류율
- AI 품질: 정답 라벨이 있는 이미지에서 품목 분류와 수량 추정 결과를 별도로 비교

측정 시 출처·표본 수·환경·실패 사례를 기록한다. AI confidence는 정확도로 간주하지 않는다.

검수 데이터에는 안전재고 0.5배·2배의 경계와 직전·직후 값을 넣는다. 승인 테스트는 미승인·승인 상태와 잘못된 관리자 이메일을 다룬다.


## 현재 상태

### 구현된 기반

- **웹:** Next.js 16/React 19 기반 로그인·가입, 대시보드, 바코드, 배송, 모니터, 리포트 화면
- **API·저장소:** Rust Axum/SQLx API와 PostgreSQL 16 스키마, Docker Compose 개발 DB
- **계정:** 회원가입·로그인·관리자 승인·창고지기 승인 API와 역할/상태 데이터
- **재고·구역:** 창고 ID 기준 목록과 CRUD, Decimal 상태 계산, 기준/포장 환산, 같은 단위 구역 집계
- **장부·감사:** 승인 대기 과거 거래, 비전 검토 대기, 담당자·출처·사유 기록, 논리 보관
- **바코드:** ZXing 판독, SKU 매칭, 소수 입출고, 로컬 JsBarcode 라벨 생성·인쇄
- **배송:** 운송장 등록, 수동 상태 전이, SweetTracker 요청형 조회 및 타임라인, 완료 후 24시간 조회 필터
- **비전:** 창고별 레퍼런스, Groq Vision 호출, 분석 로그와 승인 대기 추정치 저장

코드 구현과 API/DB 테스트 통과는 운영 배포·보안 심사·현장 장비 검증 완료를 뜻하지 않는다. AI 및 택배사 호출은 키, 계정 권한, 외부 서비스 상태에 의존한다.

### 데이터 흐름

```text
Browser -> Next.js 화면 및 /api 프록시 -> Rust Axum API -> PostgreSQL
												   -> Groq Vision (모니터 요청 시)
```

Next.js가 Rust API로 요청을 전달하고 PostgreSQL에 운영 데이터를 저장한다. 모니터 요청은 이미지와 창고 레퍼런스를 외부 모델에 보내며 결과와 일부 스냅샷을 기록한다.

### 업무별 처리 경계

- 가입·승인: 사용자 행과 상태를 저장하고, 승인 후 관리자 창고 또는 기존 관리자 창고를 연결한다.
- 재고 조정: 요청된 수량을 검증하고 서버가 `status`, `status_label`, `diff_text`, `recommendation`을 계산해 저장한다.
- 모니터링: 이미지는 요청 시 외부 AI에 전달된다. 로그 조회는 최근 50건이며 스냅샷은 전체 원본 이미지 저장소가 아니다.
- 배송: 창고 ID가 있는 배송 테이블에 운송장, 외부 택배사 단계·위치·상세 이력을 저장한다. 작업자가 요청하는 실제 조회에는 SweetTracker API 키와 사용 가능한 이용권이 필요하다.

레퍼런스 등록은 모델 재학습이 아니다. 배송은 등록 시 수동 상태 전이도 지원하지만 SweetTracker 조회 성공 시 실제 택배사 응답으로 갱신한다.

### 남은 간극

- **인증·인가:** Rust API JWT 검증, DB 계정 재확인, 역할 권한과 창고별 인가를 구현했다. 운영 배포 환경의 `JWT_SECRET`, `SUPER_ADMIN_PASSWORD` 설정 및 다계정 현장 검증이 남아 있다.
- **바코드:** ZXing 판독, SKU 매칭, 입출고 및 로컬 JsBarcode 라벨 생성 경로를 구현했다. 실제 카메라·라벨 프린터별 출력 품질 검증이 남아 있다.
- **구역 연계:** 배정 품목 중 용량 단위와 같은 기준 단위만 합산해 점유량·공실률을 계산한다. 실제 물리 용량과 품목 단위 정의의 업무 검토가 필요하다.
- **수요분석:** 최근 30일 실적·단순 과거 구간 추세와 28일 이동평균 7일 출고 기준선, 최근 7일 rolling MAPE 백테스트를 제공한다. 학습형 미래 수요예측과 권장 발주량은 없으며 운영 DB 장부가 비어 실제 MAPE는 산출되지 않았다. 품절률은 미충족 주문 이벤트 미수집으로 계산하지 않는다.
- **배송 연계:** SweetTracker 조회 경로와 타임라인 저장을 구현했다. 키 미설정은 `503`으로 실패 처리하며 외부 제공자 성공 응답 검증은 남아 있다.
- **데이터 수집:** 엑셀 레퍼런스 일괄 등록과 내보내기 UI/API를 구현했다. 업무 라벨, 사진 품질, 이미지와 품목명 매칭을 포함한 실제 데이터 운영 테스트가 남아 있다.
- **AI·외부 API·기기:** Groq Qwen 비전 모델은 합성 이미지로 WMS API 경유 호출과 승인 대기 저장을 확인했다. 이미지셋 기반 정확도는 미검증이며 SweetTracker 키/이용권과 실기기 카메라·프린터는 별도 검증해야 한다.
- **통합 자동화:** 현재 Rust 단위 테스트 5개와 수동 격리 DB/API 시나리오가 있다. 이 통합 시나리오를 CI에서 반복하는 자동화 테스트가 남아 있다.
- **현장 검증:** 실제 창고 데이터, 사용자 피드백, 프린터·카메라 호환, 성능·AI 정확도 측정이 부족하다.

### 배운 점

외부 AI 실패는 코드뿐 아니라 API 키와 계정 권한에서도 발생한다. 코드 오류와 서비스 권한을 분리 진단하고, AI 실패가 재고 CRUD에 영향을 주지 않는지 확인한다.

| P2 | SweetTracker 제공자 성공 호출 | 유효 키·이용권·실제 운송장 환경에서 검증 |
| P2 | 카메라 및 라벨 프린터 현장 검증 | 지원 브라우저·장비에서 실물 판독과 출력 확인 |
| P2 | 실데이터 수집·사용성 평가 | 데이터 출처·동의·라벨·측정 조건 기록 |

### 작업량 추정

| 작업 묶음 | 예상 소요 | 우선순위 | 선행 조건 |
|---|---:|---|---|
| JWT 환경 설정 및 권한 통합 검증 | 1~2일 | 1 | 비밀 환경변수와 테스트 사용자 |
| 승인·계정 예외 흐름 | 3~5일 | 1 | 역할 및 상태 전이 확정 |
| 재고·구역·배송 통합 검증 | 약 1주 | 1 | 테스트 계정과 초기 데이터 |
| Groq 접근 및 모니터링 검증 | 3~5일 | 2 | 키와 모델 접근 권한 |
| Rust API 배포 연결 점검 | 3~5일 | 2 | 운영 호스트와 환경 변수 |

기간은 코드 검토에 따른 추정이며 완료 보장이 아니다. 인증을 UI 개선보다 먼저 진행한다.

### 우선순위와 의존성

1. **P1, 자동 회귀:** 현재 수동 격리 DB 시나리오를 CI 자동 통합 테스트로 옮기고 다계정 권한 검증을 더한다.
2. **P2, 운영 검증:** 배포 비밀·CORS·DB 연결·보존 정책을 프로덕션 환경에서 점검한다. 로컬 검증을 운영 준비 완료로 간주하지 않는다.
3. **P2, 외부·장비 검증:** Groq와 SweetTracker 성공 호출, 카메라 판독, 라벨 실물 출력을 검증한다.
4. **P2, 실데이터 평가:** 사용자 관찰과 실제 품목 데이터를 확보한 뒤 업무 적합성과 AI 성능을 측정한다.

P1 미완료 상태에서는 UI 완성도나 AI 데모를 서비스 준비 완료 근거로 삼지 않는다.

### 범위 조정

일정이 늦어지면 고급 수요 예측, 다중 카메라, 자동 택배사 연동, 세부 UI 애니메이션과 외관 개선을 제외한다. 로그인·승인, 재고 CRUD, 창고별 데이터 경계, 핵심 구역·배송 흐름과 오류 처리는 유지한다. AI 모니터링은 외부 접근 권한이 해결되지 않으면 통합 실증 범위에서 제외하고 실패 조건과 대체 수동 검토 흐름을 문서화한다.

### 개발 자원

필요 자원은 macOS, Node.js/Next.js, Rust/Cargo, PostgreSQL 16/Docker Compose, GitHub와 AI 검증용 Groq 키·모델 권한이다. 인원·비용은 미확정이다.


## 위험·검증·요청

### 주요 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| JWT 환경 설정 누락 | 서버 관리자 로그인 거부 또는 서버 재시작 후 세션 무효화 | `JWT_SECRET`, `SUPER_ADMIN_PASSWORD`를 안전한 런타임 비밀로 설정하고 노출하지 않음 |
| Groq 모델 권한 또는 장애 | AI 모니터링 요청 실패 | 사전 모델 목록 확인, 실패 응답 보존, 재고 관리와 분리 |
| 현장 데이터 부족 | 정확도·업무 효과를 입증할 수 없음 | 테스트 데이터의 출처와 한계를 밝히고 성능 주장을 보류 |
| 외부 서비스 비용·제한 | 호출량 증가 시 테스트/운영 중단 | 호출 범위를 제한하고 비AI 핵심 기능이 독립 동작하는지 확인 |
| 프로덕션 API 미연결 | 배포 서비스에서 데이터 기능 실패 | `RUST_API_URL` 설정과 health/API 응답을 로컬 검증과 별도로 확인 |
| 일정 지연 | 핵심 검증 누락 | 고급 예측·다중 카메라·디자인 개선부터 제외 |

### 검증 방법

테스트 계정으로 가입·승인부터 재고 변경까지 재현하고, API 결과와 PostgreSQL 상태를 대조한다.

1. **업무 흐름:** 서버 관리자 승인으로 관리자 창고를 만들고, 관리자의 승인으로 창고지기를 배정한 뒤 재고를 조정한다.
2. **데이터 정합성:** 재고 경계값, 음수 입력, warehouse ID, 승인 후 소속 창고를 확인한다. 요청 대상이 아닌 창고의 데이터가 노출되면 실패다.
3. **오류 처리:** 잘못된 입력, 없는 리소스, DB 미구성, 외부 AI 오류에서 적절한 오류 응답을 확인한다. 성공으로 오인시키거나 기존 재고를 손상시키면 실패다.
4. **AI 검증:** 동일한 라벨 이미지와 설정을 기록하고 응답 필드, 로그 저장, 실패 조건을 확인한다. 정확도 기준은 이미지셋과 정답 라벨을 확보한 후 합의한다.
5. **성능:** 고정 데이터에서 주요 API 응답 시간과 오류율을 측정해 환경·표본 수와 함께 기록한다. 측정 전 임의의 목표값을 만들지 않는다.
