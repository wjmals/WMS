# Part 1. Press Release

## Headline

창고 운영자가 재고 상태와 물류 흐름을 한 화면에서 확인하는 SmartStock AI WMS 완성

## Sub-Headline

SmartStock AI WMS는 재고 수량, 안전재고, 창고 구역, 배송 상태와 이미지 기반 모니터링을 연결해 수작업 중심의 창고 운영을 데이터 기반 업무로 전환한다.

## Summary

2026년 12월 완성된 SmartStock AI WMS는 창고 운영자가 품목별 현재 재고와 안전재고를 비교하고, 부족·적정·과다 상태를 확인하며, 배송과 구역 정보를 함께 관리할 수 있는 웹 기반 창고관리시스템이다. 사용자는 역할 승인 절차를 거쳐 자신의 창고에 접근하고, 재고 변경 결과는 PostgreSQL 기반 API를 통해 저장된다.

## Customer Problem

소규모 또는 중간 규모 창고의 운영자는 재고, 구역, 배송 정보를 서로 다른 화면이나 수기 자료로 관리하기 쉽다. 현재 재고가 안전재고보다 얼마나 부족한지, 어떤 구역에 문제가 있는지, 배송 진행 상태가 어떤지 즉시 연결해 판단하기 어렵다. 실제 고객 인터뷰나 현장 통계는 아직 없으므로 특정 시간 절감률이나 오류 감소율을 결과로 제시하지 않는다. 완성 후에는 동일한 테스트 데이터로 기능 정상 작동률, 상태 판정 결과, API 성공 여부를 측정한다.

## Solution & Key Features

- 역할 기반 회원가입과 서버 관리자·창고 관리자·창고지기 승인 흐름
- PostgreSQL 기반 품목별 현재 재고·안전재고 관리
- 안전재고 기준에 따른 `shortage` / `safe` / `overstock` 상태 자동 계산
- 창고 구역, 온도, 용량 및 구역별 품목 정보 관리
- 바코드/카메라 화면에서 품목을 조회하고 재고를 조정하는 작업 흐름
- 운송장 등록, 배송 상태 진행, 배송 완료 후 24시간 목록 유지
- 창고별 이미지 레퍼런스 등록과 Groq Vision 기반 재고 모니터링 연동
- 대시보드와 리포트 화면을 통한 재고 위험 확인

## Expected Customer Value

- 운영자는 품목의 재고 상태와 조치 권고를 한 화면에서 확인할 수 있다.
- 승인된 사용자는 자신의 창고 데이터만 기준으로 업무를 수행할 수 있다.

- 운영자는 AI 결과를 무조건 신뢰하는 대신 저장된 분석 결과와 원본 상태를 함께 확인할 수 있다.

# Part 2. Main Document

## 1. Introduction

### 프로젝트 배경

창고 운영에는 품목 재고, 안전재고, 보관 구역, 배송 상태와 사용자 권한이 동시에 필요하다. 이 데이터가 분리되면 운영자는 재고 부족을 발견한 뒤 어느 구역과 배송 흐름을 함께 확인해야 하는지 판단하기 어렵다. SmartStock AI WMS는 이 데이터를 창고 단위로 묶고 API와 웹 화면으로 제공하는 것을 목표로 한다.

### 해결하려는 문제

1. 품목별 현재 재고와 안전재고를 지속적으로 비교하기 어렵다.
2. 창고 구역의 상태와 재고 정보를 별도로 관리하기 쉽다.
3. 신규 관리자와 창고지기의 접근 권한을 수동으로 관리하기 쉽다.
4. 배송 상태와 재고 운영 화면이 분리되어 출고 흐름을 함께 확인하기 어렵다.
5. 이미지 기반 재고 분석 결과를 운영 데이터와 연결하기 어렵다.

### 최종 수혜자

- 창고 관리자: 창고 단위 재고·구역·배송·사용자 승인 관리
- 창고지기: 현장 재고 조회와 수량 조정
- 서버 관리자: 관리자 가입 승인과 시스템 사용자 관리

실제 외부 고객 인터뷰와 운영 데이터는 아직 확보하지 않았으므로 고객 만족도나 운영 비용 절감 효과는 향후 검증 대상으로 둔다.

### 기존 방식의 한계

수기 장부, 개별 스프레드시트 또는 서로 다른 관리 화면만 사용할 경우 데이터 갱신 시점과 상태 기준이 달라질 수 있다. 하나의 창고 ID를 기준으로 데이터와 API를 묶고 서버에서 상태 판정 규칙을 적용하는 방식으로 이 문제를 줄인다.

### 차별점

- 역할 승인부터 실제 창고 데이터 접근까지 하나의 흐름으로 연결한다.
- 재고 상태를 안전재고 기준으로 서버에서 일관되게 계산한다.
- 구역·배송·모니터링 데이터를 동일한 warehouse ID와 연결한다.
- AI 분석 시 해당 창고에 등록된 레퍼런스 이미지를 함께 사용해 분석 근거를 창고별로 분리한다.

## 3. Tenets

**Customer First** — 사용자가 매일 수행하는 로그인, 승인, 재고 조회와 수량 조정 흐름을 가장 먼저 완성한다.

**Data-Based** — 재고 상태, API 성공 여부, AI 결과는 화면의 인상보다 테스트 데이터와 로그를 기준으로 평가한다.

**Simplicity** — 12월까지 핵심 업무 흐름에 집중하고, 검증되지 않은 RAG나 복잡한 에이전트 구조를 임의로 추가하지 않는다.

**Reliability** — AI 또는 외부 API가 실패해도 사용자가 실패 원인을 확인하고 기존 재고 데이터를 잃지 않도록 한다.

**Single Source of Truth** — 운영 데이터 저장소를 PostgreSQL/Rust API 하나로 유지하고 다른 저장소를 혼용하지 않는다.

## 4. State of the Project

### 완료된 내용

- Next.js 14 기반 로그인, 회원가입, 대시보드, 바코드, 배송, 모니터, 리포트 화면
- Rust Axum API 서버와 SQLx PostgreSQL 연결
- Docker Compose 기반 PostgreSQL 16 구성 및 `/health` 확인
- 사용자 가입, 로그인, 관리자 승인, 창고지기 승인 API
- 재고·구역·비전 레퍼런스·배송·모니터 로그 API
- 재고 생성·수정·삭제와 안전재고 상태 계산
- 배송 등록, 상태 전이, 삭제 및 24시간 필터
- 창고별 레퍼런스 이미지를 활용하는 Groq Vision 연동(레퍼런스 기반 추론)
- 관리자·창고지기 통합 승인 시나리오 및 핵심 API 통합 테스트
- API 명세서, 기능 명세서, DB 구조도 문서화

### 현재 개발 중 또는 보완이 필요한 내용

- Rust API의 서버 측 세션/JWT 인증과 역할별 API 권한 검증
- 하드코딩된 서버 관리자 계정의 secret 기반 계정 전환
- 초대된 창고지기의 기본 비밀번호를 일회성 활성화 방식으로 변경
- 사용 중인 Groq API 키 계정에서 이미지 분석 모델 접근 권한 확보
- 화면별 로딩·빈 상태·실패 상태의 일관성 검토
- 프로덕션 배포 환경에서 Rust API 연결(`RUST_API_URL`) 확정

### 현재 장점

- 데이터베이스 스키마와 Rust API의 책임이 분리되어 있다.
- 창고 ID를 기준으로 주요 데이터를 분리할 수 있다.
- 재고 상태 계산 규칙이 서버 코드에 명시되어 있다.
- 데이터 저장 경로가 PostgreSQL 하나로 단일화되어 있다.

### 현재 위험

- 브라우저 localStorage와 프론트 가드만으로는 서버 API 보안 경계를 만들 수 없다.
- 사용 중인 Groq 계정에 이미지 분석 모델 접근 권한이 없으면 AI 모니터링이 실패한다.
- 실제 현장 데이터와 고객 인터뷰가 부족해 업무 적합성을 아직 입증하지 못했다.
- 프로덕션 배포에서 Rust API가 실제로 연결되어 있는지 별도 확인이 필요하다.

## 5. Lessons Learned

### AI 모델 접근 권한 확인

- 문제: 코드는 정상이었지만 특정 Groq 모델 호출이 계속 실패했다.
- 원인: 실제 사용 중인 Groq API 키 계정에 해당 비전 모델 접근 권한이 없었다.
- 해결: 계정에서 사용 가능한 모델 목록을 직접 조회해 원인을 특정했다.
- 결과: 코드 결함과 외부 계정/권한 문제를 구분할 수 있었다.
- 배운 점: 외부 AI API 오류는 코드 검증과 별개로 계정 권한 확인을 먼저 수행해야 한다.

## 6. Strategic Priorities

**Priority 1. 핵심 업무 흐름** — 로그인, 관리자 승인, 창고지기 승인, 재고 CRUD, 구역 조회, 배송 상태 관리. WMS의 최소 사용 가능 제품을 구성하기 때문이다.

**Priority 2. 검증과 안정성** — 성공, 빈 데이터, 잘못된 입력, DB 연결 실패, 외부 AI 실패를 구분해 테스트한다. 서버 측 인증과 창고 간 데이터 격리를 보완한다.

**Priority 3. AI와 사용자 경험 개선** — 핵심 CRUD와 권한 검증이 안정화된 후 AI 모니터링 정확도, 리포트 표현, 바코드 사용성을 개선한다.

### 제외 가능한 부가 기능

일정이 지연되면 고급 수요 예측, 자동 택배사 연동, 실시간 다중 카메라, 세부 애니메이션과 디자인 개선을 후순위로 둔다. 로그인·승인·재고·구역·배송의 기본 흐름은 제외하지 않는다.

## 11. Validation Plan

**기능 정상 작동률** — 로그인, 승인, 재고, 구역, 배송, 모니터링 API를 고유 테스트 계정과 데이터로 검증하고 테스트 데이터를 정리한다.

**데이터 정합성** — warehouse ID 연결, 재고 상태 계산, 승인 후 사용자 소속을 API 응답과 PostgreSQL 레코드로 비교한다. 다른 창고의 데이터가 조회되지 않아야 한다.

**AI 기능** — 라벨이 있는 테스트 이미지를 준비해 품목명, 추정 수량, 상태, confidence를 AI 응답과 비교한다. 정확도 기준은 테스트 데이터 확보 후 정의한다.

**성능** — 고정된 테스트 데이터에서 주요 API 응답 시간과 오류율을 측정한다. 측정 전 임의의 목표 수치를 정하지 않는다.

## 12. Conclusion

SmartStock AI WMS는 재고, 구역, 배송과 사용자 승인을 하나의 PostgreSQL 기반 업무 흐름으로 연결하는 프로젝트다. 핵심 API와 화면 구조, 승인 흐름 및 통합 테스트 기반은 구현되어 있다. 앞으로는 서버 인증, 외부 AI 접근 권한, 프로덕션 배포 상태를 보완한다. 2026년 12월까지 핵심 기능의 안정성과 검증 가능성을 확보해, 창고 운영 문제를 확인 가능한 업무 흐름으로 해결하는 결과물을 목표로 한다.

# Part 3. Q&A

### 왜 이 주제를 선정했는가?

창고 운영에는 재고·구역·배송·권한 정보가 동시에 필요하지만, 이 정보가 연결되지 않는 문제를 해결 대상으로 삼았다.

### 최종 수혜자는 누구인가?

창고 관리자와 창고지기가 직접 사용자이며, 서버 관리자는 계정 승인과 시스템 관리를 담당한다.

### 왜 PostgreSQL과 Rust API를 선택했는가?

사용자, 창고, 재고, 구역, 배송처럼 데이터 관계가 뚜렷해 관계형 DB와 명확한 API 경계가 적합하다고 판단했다.

### RAG나 Tool-calling이 필요한가?

현재 핵심 기능에는 구현되어 있지 않다. 검색해야 할 문서 코퍼스나 AI가 직접 API를 호출해야 하는 요구가 확정될 때만 도입을 검토한다.

### AI가 잘못된 결과를 반환하면 어떻게 하는가?

API는 외부 응답 실패와 JSON 파싱 실패를 오류로 반환한다. confidence와 원본 이미지, 분석 이력을 함께 제공해 결과를 검토할 수 있도록 한다.

### 12월까지 구현이 가능한가?

핵심 API와 주요 화면 구조가 이미 동작하고 있어 핵심 범위는 가능하다고 판단한다. 서버 인증과 AI 접근 권한 확보가 남은 위험이다.

### 일정이 지연되면 무엇을 제외하는가?

다중 카메라, 고급 수요 예측, 자동 택배사 연동, 세부 UI 개선을 먼저 제외한다. 로그인·승인·재고 CRUD·구역·배송의 기본 흐름은 유지한다.

### 프로젝트 성공 기준은 무엇인가?

핵심 사용자 흐름을 재현할 수 있고, API 응답과 DB 상태가 일치하며, 오류와 빈 상태를 사용자가 확인할 수 있는지로 판단한다.
