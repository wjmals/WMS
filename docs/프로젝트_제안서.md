# SmartStock AI WMS 프로젝트 제안서

- 기준일: 2026년 9월
- 목표 완료: 2026년 12월

## 보도자료

### 재고와 배송 정보를 한 흐름으로 관리하는 SmartStock AI WMS

SmartStock AI WMS는 창고 운영자가 품목별 현재 재고와 안전재고, 보관 구역, 배송 상태를 한 웹 서비스에서 확인하도록 돕는 창고관리시스템이다. 사용자는 역할별 승인 절차를 거쳐 담당 창고에 접근하고, 재고 변경은 Rust API를 통해 PostgreSQL에 저장한다.

핵심 기능은 관리자·창고지기 계정 승인, 안전재고 기준의 상태 판정, 구역·배송 관리, 이미지 기반 모니터링이다. 2026년 12월까지 핵심 업무 흐름을 안정화하고 권한·오류 처리를 검증한다. AI 분석은 창고에 등록한 참고 이미지를 요청 시 함께 전달하는 방식이며 모델을 학습시키는 기능은 아니다.

이 보도자료 형식의 요약은 2026년 12월 완성을 가정한다. 실제 고객 인터뷰와 현장 운영 데이터는 아직 없으므로 시간 절감률, 오류 감소율, AI 정확도 또는 비용 절감을 성과로 주장하지 않는다. 완성 시에는 재현 가능한 테스트 계정과 데이터로 기능·정합성 결과를 공개하고, 현장 효과는 별도 실증 과제로 남긴다.

### 한눈에 보는 제안

- 고객: 재고와 출고 흐름을 관리하는 창고 관리자와 현장 창고지기
- 문제: 재고·구역·배송·승인 정보가 나뉘어 상태 확인과 조치 판단이 번거롭다.
- 제안: 창고 단위 데이터와 승인·재고 변경을 하나의 웹 업무 흐름으로 연결한다.
- 요청: 12월까지 유지할 핵심 범위와 서버 측 권한 검증 기준에 대한 검토를 요청한다.

### 완성 시 사용자가 확인할 수 있는 것

관리자는 승인된 팀원과 창고 재고를 확인하고, 창고지기는 품목의 현재량·안전량·상태를 비교한 뒤 입출고를 기록한다. 운영자는 변경 후 대시보드에서 갱신된 값을 확인하고, 필요한 경우 배송 목록과 모니터 분석 이력을 별도로 확인한다. 각 결과는 API와 데이터베이스에서 추적할 수 있게 한다.

이 약속은 시스템이 제공할 업무 기능에 한정한다. 데이터 입력 정확성, AI 추정의 신뢰성, 작업 시간 단축은 자동으로 보장되지 않는다. 재고와 배송이 자동으로 연동된다는 뜻도 아니다.

예를 들어 안전재고가 100이고 현재 수량이 40인 품목은 서버 규칙에 따라 부족으로 표시된다. 운영자는 품목을 찾아 입고량을 반영하고, 변경된 수량과 상태를 다시 확인한다. 이 시나리오는 업무 기능을 설명하는 예이며 실제 현장 데이터나 효과 측정 결과는 아니다.

프로젝트의 범위는 재고 기록과 운영 판단을 돕는 도구다. ERP 구매 발주, 공급사 주문, 택배사 실시간 추적처럼 외부 업무를 자동 실행하는 플랫폼은 아니다. 따라서 이 제안의 가치는 자동화를 넓게 약속하는 데 있지 않고, 어떤 값이 언제 바뀌었는지 확인 가능한 기본 흐름을 만들고 그 위에서 현장 요구를 검증하는 데 있다.


## 문제와 사용자

### 해결할 문제

재고, 보관 구역, 배송 정보가 서로 다른 자료에 있으면 운영자는 수량이 안전 기준에 미달했는지, 어떤 조치가 필요한지 함께 판단하기 어렵다. 관리자와 창고지기의 계정 승인 및 창고 배정이 운영 정보와 분리되면 잘못된 창고 데이터에 접근하거나 승인 상태를 따로 확인해야 한다.

현재 프로젝트는 이 문제를 해결 대상으로 설정했으며, 실제 창고 현장에서 문제가 얼마나 자주 발생하는지 조사한 자료는 아직 없다. 따라서 문제의 크기와 사용자 우선순위는 현장 인터뷰 및 테스트를 통해 확인해야 한다.

### 대상 사용자

- 창고 관리자: 창고 재고·구역·배송과 팀원 승인을 관리한다.
- 창고지기: 현장 품목을 조회하고 입출고 수량을 조정한다.
- 서버 관리자: 관리자 계정 승인과 사용자 관리를 담당한다.

### 제공 가치

창고별 재고·구역·모니터링 정보를 한 시스템에서 조회하고, 현재 재고를 안전재고 기준으로 분류한다. 재고를 조정하면 서버가 상태·차이·권고 값을 다시 계산한다. 승인된 창고지기는 담당 창고를 기준으로 조회와 조정을 수행하는 흐름을 목표로 한다.

배송은 전역 테이블에 저장되며 창고별 연결은 아직 없다. 따라서 배송과 재고가 완전히 연동된다고 설명하지 않는다. 실제 사용자 인터뷰가 없는 상태에서 업무 적합성이나 도입 효과를 확정하지 않고, 프로토타입 검토와 현장 시나리오 테스트로 먼저 확인한다.

### 기존 업무와 제안 흐름

기존 업무 방식은 본 프로젝트에서 직접 조사한 결과가 아니라 검증할 가설이다. 제안 흐름은 `가입·승인 → 창고 배정 → 재고 조회·조정 → 상태 확인 → 배송 및 모니터링 기록 확인`으로 구성한다. 데모에서는 같은 품목의 재고를 변경하고, API 응답과 저장된 값을 확인해 화면 상태가 데이터와 일치하는지 보여준다.

### 기존 방식과의 비교 가설

| 관점 | 분리된 수기·스프레드시트 방식에서 확인할 문제 | 제안 시스템이 제공하는 기준 |
|---|---|---|
| 재고 판정 | 기준량·계산 시점이 사용자마다 다를 수 있음 | 서버의 동일한 안전재고 판정 규칙 |
| 변경 추적 | 변경값과 화면 표시를 별도 확인해야 할 수 있음 | API 응답과 PostgreSQL 저장값을 대조 |
| 사용자 소속 | 계정 승인과 담당 창고 정보가 분리될 수 있음 | 승인 단계에서 warehouse ID 배정 |
| AI 결과 | 이미지 판단과 실제 재고가 따로 기록될 수 있음 | 요청 이미지 분석 결과와 모니터 로그 보관 |

이는 비교 실험을 통해 확인할 설계 가설이며 기존 제품이나 고객 업무를 조사해 얻은 결론이 아니다. 실제 운영 도입 전 현재 업무와 본 시스템을 같은 과업으로 비교하고, 누락·오입력·처리시간을 기록해야 한다.


## 해결 방향과 목표

### 제품 원칙

- **사용자 업무 우선:** 로그인·승인, 재고 조회·조정 등 일상 업무의 완결성을 우선한다.
- **데이터로 검증:** 화면 표시뿐 아니라 API 응답과 PostgreSQL 저장 결과를 함께 확인한다.
- **실패를 숨기지 않음:** DB·네트워크·AI 오류를 구분하고 성공으로 오인시키지 않는다.
- **단순한 범위 유지:** 필수 업무를 마치기 전 고급 예측, 에이전트, 다중 카메라를 추가하지 않는다.
- **효과를 과장하지 않음:** 측정하지 않은 정확도·절감 효과를 성과로 기재하지 않는다.

### 12월 완료 기준

| 범위 | 완료 조건 | 확인 자료 |
|---|---|---|
| 계정·승인 | 관리자 승인 후 창고 생성, 창고지기 승인 후 해당 창고 배정 | 가입·승인 통합 시나리오 |
| 재고 | CRUD 완료, 음수 입력 거부, 상태·차이 재계산 | API 결과와 DB 값 대조 |
| 구역·배송 | 생성·조회·수정·삭제 및 배송 상태 전이 확인 | 정상·오류·빈 데이터 테스트 |
| 보안 | 서버 측 인증·인가 적용, 창고 간 데이터 접근 거부 | 무권한·타 창고 요청 테스트 |
| 모니터링 | 설정된 API 키 환경에서 저장 성공과 실패 응답 확인 | Groq 사용 가능 여부를 포함한 테스트 기록 |

재고 상태는 현재 코드 기준으로 `current < safe × 0.5`는 부족, `safe × 0.5`부터 `safe × 2`까지는 적정, 그 초과는 과다로 분류한다. 이 경계값의 업무 적절성은 운영자 검토가 필요하다. 성능 목표와 AI 정확도 수치는 측정 데이터와 기준이 마련되기 전까지 확정하지 않는다.

### 성공 측정 방법

현재는 사용자 수, 현장 주문량, 측정된 응답 시간과 라벨이 있는 AI 이미지셋이 없다. 따라서 임의의 목표 수치를 두지 않는다. 12월 검수에서는 우선 핵심 시나리오의 통과 여부와 재고 판정 정합성을 기록한다. 이후 현장 데이터가 확보되면 다음을 측정한다.

- 업무 성공률: 사전에 정한 가입·승인·재고·배송 테스트 사례 중 통과한 사례의 비율
- 데이터 정합성: 화면·API 응답·DB에 기록된 재고와 창고 ID가 일치하는지
- 처리 성능: 고정된 데이터와 환경에서 API 응답 시간 및 오류율
- AI 품질: 정답 라벨이 있는 이미지에서 품목 분류와 수량 추정 결과를 별도로 비교

각 측정에는 데이터 출처, 표본 수, 환경, 실패 사례를 함께 기록하고, AI 신뢰도(confidence)를 정확도와 같은 값으로 해석하지 않는다.

최소 검수 데이터에는 안전재고의 0.5배·2배 경계와 그 직전·직후 수량을 포함해 판정 경계 오류를 찾는다. 승인 테스트에는 관리자 창고가 없는 상태, 승인된 상태, 다른 관리자 이메일을 지정한 상태를 포함한다. 이 사례들은 목표 수치를 만드는 대신 재현 가능한 동작 기준을 제공한다.


## 현재 상태

### 구현된 기반

- **웹:** Next.js 14 기반 로그인·가입, 대시보드, 바코드, 배송, 모니터, 리포트 화면
- **API·저장소:** Rust Axum/SQLx API와 PostgreSQL 16 스키마, Docker Compose 개발 DB
- **계정:** 회원가입·로그인·관리자 승인·창고지기 승인 API와 역할/상태 데이터
- **재고·구역:** 창고 ID 기준 목록과 CRUD, 재고 상태 계산, 구역 복합키
- **배송:** 운송장 번호 정규화, 등록, 순차 상태 전이, 배송 완료 후 24시간 조회 필터
- **비전:** 창고별 레퍼런스 저장, 최근 레퍼런스를 포함한 Groq Vision 호출 경로, 로그 저장

이는 저장소 코드에 해당 경로가 구현되어 있다는 뜻이지, 운영 배포·보안 심사·현장 검증이 끝났다는 뜻은 아니다. AI 모델 호출은 키와 계정 권한이 필요하며 외부 서비스 상태에 좌우된다.

### 데이터 흐름

```text
Browser -> Next.js 화면 및 /api 프록시 -> Rust Axum API -> PostgreSQL
												   -> Groq Vision (모니터 요청 시)
```

Next.js는 브라우저 요청을 Rust API로 전달한다. 운영 데이터의 기준 저장소는 PostgreSQL이다. 모니터 분석 요청은 이미지와 창고 레퍼런스를 외부 모델에 보내며, 분석 결과 및 일부 스냅샷을 DB에 기록하는 구조다.

### 업무별 처리 경계

- 가입·승인: 사용자 행과 상태를 저장하고, 승인 후 관리자 창고 또는 기존 관리자 창고를 연결한다.
- 재고 조정: 요청된 수량을 검증하고 서버가 `status`, `status_label`, `diff_text`, `recommendation`을 계산해 저장한다.
- 모니터링: 이미지는 요청 시 외부 AI에 전달된다. 로그 조회는 최근 50건이며 스냅샷은 전체 원본 이미지 저장소가 아니다.
- 배송: 운송장 번호와 상태를 전역 테이블에 저장한다. 현재 상태 변경은 외부 운송장 추적 결과가 아니라 API 상태 전이 요청으로 이뤄진다.

이 경계를 분명히 하는 이유는 화면의 표현을 실제 자동화 범위보다 넓게 설명하지 않기 위해서다. 특히 레퍼런스 등록을 모델 재학습으로, 상태 전이를 택배사 실시간 조회로 오해하지 않도록 사용자에게 표시해야 한다.

### 남은 간극

- **인증·인가:** 로그인 상태는 브라우저 localStorage와 화면 가드 중심이다. Rust API의 서버 측 세션/JWT 권한 검사가 없어 운영 전에 보완해야 한다.
- **바코드:** 현재 화면은 품목 ID/이름을 입력해 찾고 카메라 미리보기를 제공한다. 카메라 프레임의 실제 바코드 판독은 확인되지 않았다.
- **구역 연계:** 구역 CRUD는 있으나 현재 재고 총량으로 공실률을 계산한다는 근거는 없다.
- **배송 연계:** 배송 정보는 전역 테이블이며 재고 또는 창고와 외래 키로 연결되지 않는다. 실시간 택배사 조회 기능도 확인되지 않았다.
- **AI·배포:** Groq 모델 권한 및 배포 환경의 Rust API 연결을 검증해야 한다.
- **현장 검증:** 실제 창고 데이터, 사용자 피드백, 성능·정확도 측정이 부족하다.

### 배운 점

외부 AI 호출 실패는 코드 오류 외에 API 키와 계정별 모델 접근 권한에서도 발생할 수 있었다. 따라서 요청 생성·응답 파싱 같은 코드 검증과 외부 서비스 권한 확인을 분리하고, AI 실패가 재고 CRUD 실패로 전파되지 않는지도 점검한다.

추정치는 코드 검토에 따른 일정 계획이며 실제 투입 시간이나 완료 보장은 아니다. 인증 작업은 UI 개선보다 먼저 진행한다.

### 우선순위와 의존성

1. **P1, 보안 경계:** 인증 방식과 창고별 인가를 먼저 결정한다. 보호된 화면뿐 아니라 API 요청 자체가 사용자 소속을 검증해야 한다.
2. **P1, 업무 완결성:** 계정 승인, 재고 CRUD, 구역·배송 흐름을 성공·실패·빈 데이터까지 확인한다.
3. **P2, 운영 검증:** Rust API 배포 주소, CORS, DB 연결과 로그를 점검한다. 로컬 동작은 프로덕션 동작의 증거로 대체할 수 없다.
4. **P2, AI 검증:** 모델 호출 권한과 테스트 이미지를 확보한 후 분석 결과 및 저장 동작을 평가한다.
5. **P3, 개선:** 사용자 관찰 결과를 받은 뒤 리포트 표현과 바코드 작업 편의성을 조정한다.

P1 항목이 미완료인 상태에서는 UI 완성도나 AI 데모를 전체 서비스의 준비 완료 근거로 삼지 않는다.

### 범위 조정

일정이 늦어지면 고급 수요 예측, 다중 카메라, 자동 택배사 연동, 세부 UI 애니메이션과 외관 개선을 제외한다. 로그인·승인, 재고 CRUD, 창고별 데이터 경계, 핵심 구역·배송 흐름과 오류 처리는 유지한다. AI 모니터링은 외부 접근 권한이 해결되지 않으면 통합 실증 범위에서 제외하고 실패 조건과 대체 수동 검토 흐름을 문서화한다.

### 개발 자원

개발 환경은 macOS, Node.js/Next.js, Rust/Cargo, PostgreSQL 16/Docker Compose, GitHub이며 AI 모니터링 검증에는 사용 가능한 Groq API 키와 비전 모델 권한이 필요하다. 실제 인원 구성이나 비용 정보는 확정되지 않아 별도 추정하지 않는다.

### 검증 방법

테스트 계정으로 가입·승인부터 재고 변경까지 재현하고, API 결과와 PostgreSQL 상태를 대조한다.

1. **업무 흐름:** 서버 관리자 승인으로 관리자 창고를 만들고, 관리자의 승인으로 창고지기를 배정한 뒤 재고를 조정한다.
2. **데이터 정합성:** 재고 경계값, 음수 입력, warehouse ID, 승인 후 소속 창고를 확인한다. 요청 대상이 아닌 창고의 데이터가 노출되면 실패다.
3. **오류 처리:** 잘못된 입력, 없는 리소스, DB 미구성, 외부 AI 오류에서 적절한 오류 응답을 확인한다. 성공으로 오인시키거나 기존 재고를 손상시키면 실패다.
4. **AI 검증:** 동일한 라벨 이미지와 설정을 기록하고 응답 필드, 로그 저장, 실패 조건을 확인한다. 정확도 기준은 이미지셋과 정답 라벨을 확보한 후 합의한다.
5. **성능:** 고정 데이터에서 주요 API 응답 시간과 오류율을 측정해 환경·표본 수와 함께 기록한다. 측정 전 임의의 목표값을 만들지 않는다.

### 검토 및 결정 요청

12월까지 우선 유지할 업무 범위, 서버 인증·인가의 완료 기준, 창고 간 데이터 격리 테스트 방법을 검토해 달라. 실사용자 인터뷰와 테스트 데이터 확보를 위한 연결도 요청한다. 이는 기술 선택 자체에 대한 승인보다, 무엇을 완성으로 볼지와 어떤 근거로 평가할지를 합의하기 위한 요청이다.

### 발표 시 답할 질문

**왜 관계형 DB와 Rust API인가?** 사용자·창고·품목의 관계와 제약을 데이터베이스에서 표현하고, 프런트엔드와 저장소 사이에 명시적인 API 경계를 두기 위해서다. 선택의 성능 우위는 별도 측정한 사실이 아니다.

**AI가 틀리면 어떻게 하는가?** 분석 결과와 신뢰도, 근거 텍스트 및 로그를 확인할 수 있도록 하고 재고 조정 전 사람이 결과를 검토하는 흐름을 유지한다. 현재 AI 추정만으로 재고를 확정하는 정확도 보장은 없다.

**일정이 지연되면 무엇을 지키는가?** 서버 권한 검증, 승인, 재고 데이터 정합성과 오류 처리를 남기고, 고급 예측·자동 택배 연동·다중 카메라를 제외한다.

**프로젝트 성공은 무엇으로 판단하는가?** 정해 둔 핵심 시나리오가 재현되고, 화면·API·DB가 일치하며, 실패 조건을 숨기지 않는지로 판단한다. 사업 효과는 현장 비교가 완료되기 전까지 결론 내리지 않는다.
